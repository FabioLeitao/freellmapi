# M1.1 — Block-cause para tipos de imagem (PNG/JPEG)

## Objetivo
Implementar o cabeçalho `X-Block-Cause` e `X-Block-Cause-Detail` nas respostas 429 para requests de imagem, distinguindo entre PNG e JPEG, e garantindo que o header `X-Vision-Model-Available` seja incluído corretamente. A mudança segue o PR #2118 (feat: report a distinct block cause on 429) e as issue #2061/#2062.

## Risco: baixo
Mudança localizada no módulo `block-cause.ts` e routes afetadas (`proxy.ts`, `responses.ts`, `inbound-chat.ts`). Não toca infraestrutura, dados de usuários ou lógica de negócio. Sem migração de banco.

- **R0.5** — Header `X-Vision-Model-Available` deve indicar modelo disponível quando applicable

## Contrato

### POST `/v1/chat/completions`
| Campo | Descrição |
|------|----------|
| `status` | 429 quando quota esgotada ou modelo em cooldown |
| `X-Block-Cause` | `vision_quota_exhausted` / `cooldown` / `no_vision_model` |
| `X-Block-Cause-Detail` | `cooldown` / `key_quota` / `no_vision_model` |
| `X-Vision-Model-Available` | `true`/`false` — indica se há modelo de visão disponível |

### POST `/v1/responses`
| Campo | Descrição |
|------|----------|
| `status` | 429 quando quota esgotada ou modelo em cooldown |
| `X-Block-Cause` | Igual ao `/v1/chat/completions` |
| `X-Block-Cause-Detail` | Igual ao `/v1/chat/completions` |
| `X-Vision-Model-Available` | Igual ao `/v1/chat/completions` |

### Lógica de detecção de tipo de imagem
- **PNG** (`data:image/png;base64,`): identificado pelo tipo `image_url` com base64 começando por `iVBORw0KGgo=`
- **JPEG** (`data:image/jpeg;base64,`): identificado pelo tipo `image_url` com base64 começando por `/9j/4AAQSkZJRg==`
- Quando `requireVision: true` (image em request), o `block-cause.ts` deve filtrar a linha "vision" antes de computing o base cause
- Quando `requireVision: false` (text-only), o cause é o base sem prefixo "vision_"

## Modelo de dados
Nenhuma mudança em banco de dados. Mudanças apenas em headers de resposta e lógica de filtro em `block-cause.ts`.

### Caminhos de erro e falha
- Entrada inválida de image_url → 400 bad request (já tratado por validação upstream)
- Modelo suporta visão mas chave expirada → 401 (já tratado)
- Concorrência de múltiplas requisições simultâneas → testar com `--pool=forks`; o `block-cause.ts` é stateless, mas o ledger de cooldown é shared

## Riscos e pontos de atenção
- **Fácil de errar:** confundiR `422` (vision gate) com `429` (fallback loop). O `422` não deve ter `X-Block-Cause` header (é tratado separadamente).
- **Pode quebrar outra parte:** se o filtro `requireVision` for aplicado incorretamente em requests text-only, pode adicionar header desnecessário.
- **Cuidado com dados existentes:** não há mudança de dado persistente; risco é apenas na lógica de resposta.

## Fora do escopo
- Mudança de modelo de banco de dados
- Nova funcionalidade de cobrança/assinatura
- Mudança na arquitetura do router ou rate-limit ledger
- Suporte a novos provedores de visão

## Decisões
1. O header `X-Block-Cause` será incluído **apenas** em status 429 (fallback loop), não em 422 (vision gate).
2. O header `X-Vision-Model-Available` indica se há algum modelo de visão disponível (considerando cooldown e quota).
3. Distinção PNG vs JPEG é feita pelo prefixo do `data:image/` no `image_url` — não faz download nem processamento da imagem.
4. O mesmo block-cause é retornado tanto para `/v1/chat/completions` quanto para `/v1/responses`, garantindo consistência.
