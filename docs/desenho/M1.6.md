# Desenho M1.6: registrar o cliente em toda linha `start/ok/fail` do roteador

Issue #30. Base: `main` do fork / `upstream/main` (o código tocado é do upstream). Patch ao upstream,
separado (uma mudança por PR); nada no upstream durante a trava. Os arquivos de gerência do fork
(`docs/fork/README.md`) **não** entram no branch de patch (ADR-001).

## Objetivo

Toda linha de rastreio do roteador (`[Proxy]` e `[Responses]`, eventos `start`/`next`/`ok`/`fail`) passa a
trazer `client=<agent>`, derivado do classificador já existente (`lib/client-classifier.ts`) pelo
`User-Agent`/cabeçalhos estáveis. Nenhum User-Agent cru, IP, e-mail ou dado de cliente entra no log:
só o enum `ClientAgent`. A causa do sumiço do `client_agent` fica registrada num README só do fork.

## Risco

`padrão`: toca o caminho quente de log do proxy/responses; a mudança é um token por linha, sem dado
bruto, autenticação ou banco. O ponto sensível é R16 (não logar o User-Agent cru) e a docs ficar no
lugar certo (fora do patch ao upstream).

## Diagnóstico da causa (confirmado no clone, 2026-11-27)

- As linhas citadas na issue vêm de `traceRouteEvent` (`server/src/routes/proxy.ts:138`), chamado 12 vezes
  em `proxy.ts` e 5 em `responses.ts`. O formato atual é
  `[Proxy] <hh:mm:ss> <evento> <id6> a<n> <plataforma> - <modelo> [req=…] [lat=…]`:
  **não há campo de cliente em nenhuma versão canônica**.
- `git log --all -S'client_agent='` e `git log --all -S'client=' -- server/src/routes/proxy.ts
  server/src/routes/responses.ts` não retornam nenhum commit: o campo nunca esteve nessas linhas no
  histórico do clone. Não é regressão de um arquivo do upstream.
- O que existe é `client_agent` como **coluna de `requests`**, escrita por `logRequest()`
  (`lib/request-log.ts`) a partir de `getClientContext()`; o middleware `clientContextMiddleware` está
  montado em `app.ts:238` e o classificador cobre `opencode`, `deepseek-harness` (dsh-tui), `hermes-agent`,
  `cursor`, `zero` etc. Ou seja: o dado sempre foi classificado e gravado no banco, nunca impresso na
  linha do roteador.
- A observação de 23/nov (`client_agent=deepseek-harness` em linhas do roteador) só pode vir de um build
  local com patch fora do histórico canônico — a imagem de dogfooding
  `up-8fcdb90e.databoar-01474fe1.zeroclassifier`, cujo merge `01474fe1` está solto (só por reflog,
  `docs/operacao.md`). Não há como provar o conteúdo exato daquele merge sem o `:3001`, que esta tarefa
  não toca. O que se pode afirmar com evidência: o `main` e o `upstream/main` nunca imprimiram o cliente;
  a mudança deste desenho passa a imprimi-lo em qualquer build feito do código canônico.

## Contrato

### Linha de log

Em `traceRouteEvent` (`server/src/routes/proxy.ts`), um token extra, logo depois do evento:

```
[Proxy] 20:41:03 start client=opencode a0 z-ai/glm-5.3-flash - z-ai/glm-5.3-flash req=auto
```

Regras:

- `client=<agent>` aparece **exatamente uma vez** em toda chamada de `traceRouteEvent`, para os eventos
  `start`, `next`, `ok` e `fail` e para os dois scopes (`Proxy`, `Responses`).
- O valor vem de `opts.clientAgent` quando informado; senão de `getClientContext().agent`. Sem contexto
  (chamada direta em teste, job de fundo) ou com `REQUEST_ANALYTICS_LOG_CLIENT=false`, o valor é
  `unknown`. Nunca é o `User-Agent` cru.
- `opts.clientAgent?: ClientAgent` é opcional e serve só para testes e superfícies futuras; os 17
  chamadores atuais não mudam.
- Nenhum outro token da linha muda: tempo, evento, id curto, `a<n>`, plataforma, `-`, modelo, `req=`,
  `lat=`, `in=`, `out=` e `err=` permanecem iguais, na mesma ordem.
- A classificação continua sendo a de `lib/client-classifier.ts`: não criar regex nova em `traceRouteEvent`.

### README do fork

Arquivo novo, só do fork: `docs/fork/README.md`. Seção "Como ler por cliente nos logs" com:

1. o formato da linha e o significado de `client=`;
2. exemplos somente leitura, sem tocar no serviço:
   `podman logs freellmapi_freellmapi_1 | grep 'client=opencode'` (e `hermes-agent`, `dsh-tui` →
   `deepseek-harness`, `cursor`);
3. o diagnóstico acima (a coluna `requests.client_agent` sempre existiu; as linhas do roteador nunca a
   tiveram no código canônico; builds locais fora do histórico podem ter tido patch próprio);
4. o limite de privacidade: só o enum é logado; `unknown` quando o contexto não existe ou o opt-out
   `REQUEST_ANALYTICS_LOG_CLIENT=false` está ativo.

O `README.md` da raiz é do upstream: **não** editar. `docs/fork/README.md` nunca vai em branch de patch.

## Riscos e pontos de atenção

- **R16:** nunca concatenar `req.headers['user-agent']`, `req.ip` ou o texto do erro. O valor é o enum da
  `ClientAgent`, que já passou por validação no classificador.
- `traceRouteEvent` roda fora de escopo de request nos testes unitários; por isso o `unknown` é
  obrigatório e não pode virar exceção (o log não pode derrubar a requisição).
- A linha é consumida por `grep` de operador: manter `client=` sem espaços e numa posição fixa, antes do
  id curto, para `grep 'client=opencode'` funcionar sem regex.
- Classificador novo (um harness que ainda não é reconhecido) é trabalho de `client-classifier.ts`,
  não deste desenho: aqui só se imprime o que ele já decide.
- A causa documentada é a que o histórico prova; não afirmar que um patch específico do `01474fe1`
  continha o campo — ele não está no clone. O README diz explicitamente esse limite.

## Fora do escopo

- Melhorar o classificador ou adicionar novos harnesses: `lib/client-classifier.ts` é do upstream e muda
  por tarefa própria.
- Escrever `client_agent` em `requests`: já existe (`logRequest`), não mexer.
- Mexer no `:3001`, no contêiner em uso ou no banco real: só leitura de logs pelo operador, via README.
- Editar o `README.md` da raiz (do upstream).

## Decisões

- ADR-019: o cliente das linhas do roteador vem de `getClientContext().agent`/`ClientAgent`, com
  `unknown` seguro; a causa do sumiço e o modo de leitura moram em `docs/fork/README.md`.
