# Desenho F0.7: fluxo de um patch até o upstream

Issue #13. Base: `main` do fork (somente documentos). Fixa, como ADR, o rascunho de
`docs/operacao.md`; não há ADR de fluxo em `docs/decisoes.md` até hoje (conferido: ADR-001 a ADR-020
cobrem convenções, migração, testes, build e publicação, mas não o caminho do patch). Este desenho é a
referência; o ADR é ADR-017 em `docs/decisoes.md`. Nada muda no upstream.

## Objetivo

Uma sequência única e verificável para levar um patch do fork ao `tashfeenahmed/freellmapi`: branch de
`upstream/main`, gate local no SHA exato, PR de revisão no fork que não é mesclado, e abertura no upstream
só com validação local e o "vai" do usuário, um PR por vez. O que é só do fork segue outro caminho.

## Risco

`padrão`: é uma decisão de processo, sem código nem dado; um erro aqui pode abrir PR no upstream sem
validação ou sem o "vai", por isso não é `baixo`.

## Requisitos e testes do plano

R19, R20. T0.6, T0.7, T0.8, T0.9 (provas de processo, não comportamento do produto).

## Contrato (fluxo)

1. **Sincronizar e cortar o branch.** Atualizar `upstream/main`; criar o branch de patch **dela**, nunca
   do `main` do fork. Um branch por mudança. O branch não contém `docs/operacao.md`, `docs/plano.md`,
   `docs/custos.md`, `docs/arquitetura.md`, `docs/decisoes.md`, `docs/desenho/`, PDFs nem
   `.claude/agent-memory/`. Push só para `origin`; nunca `git push upstream`.
2. **Implementar e testar no SHA exato.** Uma mudança por PR, com teste que exercita a mudança de verdade
   e `npm test` verde. Regras do `CONTRIBUTING.md`: `.editorconfig` e tsconfig, sem reformatação fora do
   diff, nenhum limite/id de modelo/endpoint inventado (fonte oficial conferida), nenhum serviço pago ou
   que peça cartão; migração só em arquivo novo em `server/src/db/migrations/`, sem editar migração
   aplicada; `npm run check:i18n` em `client/`. PR sempre pronto, nunca draft.
3. **Gate local no SHA que vai subir.** Com `scripts/check-all.sh` (F0.10, #26) quando existir; até lá,
   os mesmos passos na mesma ordem: `npm ci`, `npm run test:migrations`, `npm test`, `npm run lint`,
   `npm run build`, `npm --prefix client run check:i18n`. Sem Docker, sem `:3001` e sem banco real.
   Só se segue com saída 0; copiar a saída para o PR. Nunca baixar rigor para dar verde.
4. **Validar localmente no fork e no `:3001`.** A trava do `docs/operacao.md` vale: nenhum PR, issue,
   comentário ou reação no upstream antes de a mudança estar validada localmente; **quem decide que está
   validada é o usuário**. Essa validação é uma etapa do processo, não uma suposição do agente.
5. **PR de revisão no fork, não mesclado.** Contra o `main` do fork, com `--repo FabioLeitao/freellmapi`.
   Nele rodam CI, `revisor-senior`, `cyber-senior` (KP) e o adversarial (Hermes), e o gate da etapa 3 é
   repetido no head final. O PR de revisão **não é mesclado no fork**.
6. **Abertura no upstream, com o "vai".** Com as revisões/CI verdes, a validação local do usuário e o
   "vai" **desse PR específico**, o PM abre o PR no `tashfeenahmed/freellmapi` com o mesmo branch/SHA.
   Todo comando de escrita leva `--repo` explícito. Um "vai" não autoriza o PR seguinte.
7. **Depois do PR no upstream.** Quem mescla é o mantenedor; `merge-green` não se aplica ao upstream. O
   PR de revisão no fork é fechado (sem mesclar) e o fork recebe o patch na próxima sincronização (F0.6).

**Fora deste fluxo:** mudança que só interessa ao fork, ou que o upstream recusar, vai por PR no fork
com `merge-green` (o PM não roda `gh pr merge` neste repo). O `docker.yml` do fork constrói em PRs e não
publica (ADR-009). Se a sincronização do upstream alterar as mesmas linhas, prevalecem a intenção deste
fluxo e a regra de uma mudança por PR.

## Especificação para o TDD do dev (provas de processo, sem produto)

Nenhum teste de código. As provas são comandos de leitura, executáveis no clone canônico, determinísticos
e sem escrita no upstream:

- **DF0.7-1** — dado o branch de patch, quando roda `git merge-base --is-ancestor upstream/main HEAD`,
  então saída 0 (T0.6 aplicado ao branch, não só ao `main`).
- **DF0.7-2** — dado `git diff --stat upstream/main...<branch>`, então só aparecem arquivos da mudança;
  nenhum de `docs/`, `.claude/`, PDF, `docs/operacao.md` ou `docs/plano.md` (T0.7).
- **DF0.7-3** — dado o SHA final, quando roda o gate da etapa 3, então saída 0; um teste quebrado de
  propósito faz a saída diferente de 0 (T0.8).
- **DF0.7-4** — dados os comandos de escrita do fluxo, quando inspeciono o comando de abertura do PR no
  upstream, então ele leva `--repo tashfeenahmed/freellmapi`, é o único desse tipo e vem depois do "vai"
  registrado na issue (T0.9, por construção do processo; nenhuma verificação automática prova o "vai").
- **DF0.7-5** — dado o PR de revisão no fork, quando consulto o estado com `--repo FabioLeitao/freellmapi`,
  então ele está aberto ou fechado sem merge; `merged_at` é nulo.
- **DF0.7-6** — dado um pedido de mudança que só interessa ao fork, quando sigo o fluxo, então o PR é no
  fork, com `merge-green`, e nenhum branch nasce de `upstream/main` para ele.

## Riscos e pontos de atenção

- A trava do upstream não é permissão de token: mesmo com escopo de escrita, nenhum agente escreve no
  upstream sem validação local e o "vai" do usuário. `gh` com `--repo` explícito é a única forma segura.
- O "vai" é por PR: não reutilizar uma autorização dada para patch anterior.
- O PR de revisão no fork não pode ser mesclado: se for, o fork passa a ter conteúdo que devia viajar
  como patch e a próxima sincronização conflita.
- `scripts/check-all.sh` ainda não existe no checkout (F0.10 desenhada, não entregue). Até ela existir, o
  gate da etapa 3 é a sequência equivalente — sem pular passo e sem `|| true`.
- Não confundir a validação no `:3001` (feita pelo usuário) com os testes automatizados: estes nunca
  tocam o contêiner nem o banco real (ADR-005).

## Fora do escopo

- Criar ou mesclar PRs nesta rodada: o PM abre o PR no upstream; o merge é do mantenedor.
- Proteção do `main`: F0.3 (#10). Gate local: F0.10 (#26). Sync: F0.6 (#12).
- Publicação de imagem pelo fork: ADR-009 / F0.9.

## Decisões

- ADR-017: fluxo único de patch até o upstream, com branch de `upstream/main`, gate local, PR de revisão
  no fork não mesclado e abertura no upstream só com validação local e o "vai" por PR.
