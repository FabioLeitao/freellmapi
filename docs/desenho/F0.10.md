# Desenho F0.10: gate local `scripts/check-all.sh` do fork

Issue #26. Base: `main` do fork. Arquivo **só do fork** (ADR-001): não entra em branch de patch nem vai ao
upstream. Sem PR e sem build para gravar este desenho.

## Objetivo

Um único comando na máquina do operador que reproduz o que o `ci.yml` executa, na mesma ordem, e só sai 0
quando tudo passa. Roda no Node do host por padrão (ADR-005); o modo opcional em podman usa um contêiner
sem portas publicadas. Nenhum passo sobe o `docker-compose.yml`, reinicia o `:3001` ou abre `freeapi.db`.

## Risco

`padrão`: é um script local de verificação, não infraestrutura implantada; um erro nele pode dar falso
verde, por isso a prova de falha (DF0.10-2/3) é parte do contrato. Não toca dados, segredos nem autenticação.

## Requisitos e testes do plano

R12, R14, R25. T0.11.

## Contrato

### Entrada

`scripts/check-all.sh [--container [IMAGEM]]`

- Sem argumentos: roda no Node do host. CWD é a raiz do repositório (`cd "$(dirname "$0")/.."`), qualquer
  que seja o diretório de chamada.
- `--container` (imagem padrão `node:24.22.1-bookworm-slim`, a base do `Dockerfile`): reexecuta o próprio
  script dentro de `podman run --rm`, com o repositório montado em `/app`, sem `-p`/`--publish`, sem
  `--network=host`, sem montar socket do Docker e com `FREELLMAPI_CHECK_ALL_IN_CONTAINER=1` para impedir
  recursão. A imagem pode ser sobrescrita pelo segundo argumento. Se `podman` faltar, falha com mensagem
  clara: não cai silentemente para o host.
- `FREELLMAPI_CHECK_ALL_IN_CONTAINER=1` com `--container` é erro de uso (recursão).

### Saída e efeitos

Passos, nesta ordem, com `set -euo pipefail` e um banner nomeando cada um:

| # | Comando | Origem |
|---|---|---|
| 1 | `npm ci` | `ci.yml`, "Install dependencies" |
| 2 | `npm run test:migrations` | `ci.yml`, "Check migration round trip" |
| 3 | `npm test` | `ci.yml`, "Run tests" (encadeia bootstrap, hooks, server, cli e client) |
| 4 | `npm run lint` | `ci.yml`, "Lint" (server e cli; client fora) |
| 5 | `npm run build` | `ci.yml`, "Build workspaces" |
| 6 | `npm --prefix client run check:i18n` | `client/package.json`, exigido por R18/R25 |

O passo 6 é explícito mesmo já sendo chamado por `npm test -w client`: é barato e torna a checagem
visível no banner. Não se define `COVERAGE` (o CI só a usa no Node 22), não se liga lint do client e não
se roda `desktop/` (fora da cadeia da raiz, conforme `docs/arquitetura.md`).

Saída 0 **somente** se os seis passos saírem 0. Qualquer falha encerra na hora, com o número e o nome do
passo, sem `|| true`, `continue-on-error`, `[skip ci]`, `--no-verify` ou retry que esconda a causa. Nenhum
comando do script escreve em `server/data/`, abre `freeapi.db`, publica porta ou chama `podman-compose`.

## Modelo de dados

Nada.

## Especificação para o TDD do dev

Arquivo de teste: `scripts/check-all.test.mjs`, rodado com `node --test scripts/check-all.test.mjs`. Ele
não entra em `npm test` da raiz: isso exigiria mudar `package.json` (arquivo do upstream, ADR-001). O teste
usa um executável `npm` fictício primeiro no `PATH`, que registra os argumentos em `$CHECK_ALL_LOG` e
sai conforme `CHECK_ALL_FAIL_ON` (nome do passo). Nenhum `npm ci` real, nenhuma rede, nenhum banco.

- **DF0.10-1** — dado o shim sempre verde, quando roda `scripts/check-all.sh`, então sai 0 e o log é
  exatamente, em ordem: `ci`, `run test:migrations`, `test`, `run lint`, `run build`,
  `--prefix client run check:i18n`.
- **DF0.10-2** — dado `CHECK_ALL_FAIL_ON=run test:migrations`, quando roda, então sai diferente de 0, o
  banner names o passo 2 e o log não contém `test` nem nenhum passo posterior.
- **DF0.10-3** — dado `CHECK_ALL_FAIL_ON=run build`, quando roda, então sai diferente de 0 e o log termina
  no passo 5 (o `check:i18n` explícito não roda).
- **DF0.10-4** — dado chamada a partir de `/tmp` (ou outra pasta), quando roda o caminho absoluto do
  script, então todos os comandos do shim são registrados com `cwd` igual à raiz do repositório.
- **DF0.10-5** — dado o conteúdo de `scripts/check-all.sh`, quando procura por `3001`, `freeapi.db`,
  `docker-compose`, `podman-compose`, `|| true`, `continue-on-error`, `--no-verify` e `npm install`, então
  nenhum desses textos aparece (comentários incluídos, para não deixar instrução enganosa).
- **DF0.10-6** — dado um shim `podman` que registra os argumentos e um shim `npm` verde, quando roda
  `scripts/check-all.sh --container`, então o comando do podman contém `--rm`, `--entrypoint`, a montagem
  do repositório e `FREELLMAPI_CHECK_ALL_IN_CONTAINER=1`, e **não** contém `-p`, `--publish` nem
  `--network=host`; dentro do contêiner simulado os seis passos rodam uma vez só.
- **DF0.10-7** — dado `FREELLMAPI_CHECK_ALL_IN_CONTAINER=1`, quando roda com `--container`, então sai
  diferente de 0 com mensagem de recursão, antes de chamar podman.
- **DF0.10-8** — dado um shim `podman` que sai 127, quando roda com `--container`, então sai diferente de
  0 e o host não executa nenhum passo (o log de `npm` fica vazio).

## Especificação para a aceitação do QA

Caixa-preta, no host, com o `:3001` no ar (é a condição de T0.11: o gate tem de conviver com ele).

- **AF0.10-1** — dado o `:3001` respondendo e um `freeapi.db` real com contagem conhecida de linhas, quando
  roda `scripts/check-all.sh` num SHA verde, então a saída é 0, o contêiner segue respondendo e a contagem
  do banco é a mesma de antes (o script nunca abre o banco real).
- **AF0.10-2** — dado um teste de propósito quebrado no SHA, quando roda o gate, então a saída é diferente
  de 0, o banner aponta o passo, e o operador consegue ver a falha sem reexecutar só o teste que caiu.
- **AF0.10-3** — dado `scripts/check-all.sh --container`, quando roda, então nenhuma porta é publicada no
  host, o `:3001` continua com a mesma resposta e o resultado é o mesmo dos seis passos do host.

## Riscos e pontos de atenção

- `npm ci` apaga e reinstala `node_modules`: é o que o CI faz e é necessário para o gate valer; nenhum
  outro comando de instalação entra.
- A ordem dos passos é contrato: mudar a ordem ou pular o `check:i18n` é mudança de desenho, não
  "otimização". O `npm test` da raiz encadeia com `&&`: já por isso uma falha no server esconde cli/client,
  e o banner do script é a única pista do passo que parou.
- Modo container: uma imagem com Node diferente pode recompilar nativos (`better-sqlite3`); por isso ele
  é opcional e o padrão continua sendo o Node do host (ADR-005). Nunca usar `--network=host`: o cliente
  do gateway pode estar no `:3001` e o gate não deve sequer poder alcançá-lo.
- Não transformar este script em gancho de commit: um commit só de `docs/` ou memória não deve depender
  de `npm ci` (o hook opcional do repo só injeta o checklist do `CONTRIBUTING.md`).

## Fora do escopo

- Mudanças em `package.json`, `ci.yml` ou config do vitest para registrar o teste do gate: seria divergência
  do fork em arquivo do upstream (ADR-001; F0.9 só mexe nos workflows do fork).
- Proteção do `main`: F0.3 (#10).
- Publicar imagem ou rodar o build do wrapper: F0.5 (#11) e `docs/operacao.md`.

## Decisões

- ADR-012: gate local único, no host por padrão, container opcional sem portas, sem baixar rigor e sem
  arquivo de gerência em branch de patch.
